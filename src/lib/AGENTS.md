- Site themes live in `site-theme.ts`: the switch offers only dark and light, dark is the default, and `readSiteTheme` maps any older stored value (including the retired festival choices) to dark; `__root.tsx` applies the saved theme before first paint with an inline boot script mirroring these rules (keep both in sync), and `applySiteTheme` clears any leftover retired theme classes, so a theme can be retired without leaving its styles or pictures on screen.
- Education Support rules and payment-page links are browser-safe and tested; acknowledgement numbers come only from database triggers/one RPC with a per-form counter table (date + state + form code + serial; form codes mirrored in `education-support/numbering.ts`), preserving earlier references. Bank/KYC text is AES-GCM encrypted server-side, excluded from drafts/PDF/export, and decrypted only after admin authorization; the key is EDUCATION_KYC_ENCRYPTION_KEY or, when unset, one derived from the server-only database secret (`kyc-key.server.ts`, so hosts without the dedicated key still encrypt; never change either once data exists); with neither the save is refused with a reference (no plaintext); approval is guarded by a database trigger requiring confirmed payment.
- Education staff access is separate from profiles; admin-assigned verified BDE/BDM accounts receive only own/team referral summaries without contact or KYC data and cannot confirm payments or approve applications.
- CRM memberships and employee profiles stay separate; RLS helper functions enforce own/team access, atomic invoker RPCs create/import leads, admin-only verified-account onboarding assigns access, and exact-reference support lookup projects only safe fields; the scholarship acknowledgement PDF in a lead is rebuilt in the browser from PDF-only fields, read after the caller's own RLS confirms they can see that lead. The private workspaces (Admin, CRM, BDE/BDM, My Volunteers, Volunteer) share `components/dashboard/shell.tsx` and the `.dash-shell` palette, separate from public site decoration.
- Website form → CRM lead routing lives in one AFTER INSERT database trigger per submission table (security definer, contact fields only, never bank/KYC, failures never block the submission), resolving the entered code to an active employee; unmatched leads stay ownerless for admin assignment via an RPC, so every form path routes identically.
- Builds served outside Lovable hosts forward scholarship actions to the published address in `education-support/remote.ts` (empty until published) via `/api/public/education/$action`; public form CORS allows HTTPS origins without cookies and keeps validation and rate limits, so credentials stay server-only.
- The scholarship form is staged (basic details stay on the device until the payment ID is shared, which then creates the row with an internal `R` Registration ID that the student sees only after sharing a payment ID, shown then beside the ack number; the database swaps it for the real ack number when a payment ID is saved, keeping the old ID in `registration_id` and renaming the sheet row in place; then the rest) and reopens with ack or Registration ID + date of birth + state + registered mobile (every reopen/save/submit re-checks all four and wrong attempts are rate-limited per reference); students pass the payment step and final submission only after a payment ID is shared (checked in the browser and on the server, admins exempt), so no unpaid form is completed. A Google Sheet keyed by ack number mirrors every start/submit/payment ID (masked bank/Aadhaar only, matched by header, grid grows itself); when the database fails at any step the sheet takes the change instead (new rows get a `B`-prefixed backup ack; rows already in the database are marked "Update pending" and copied back on the next reopen/final submit or admin sync), and visitors only see plain messages, never database errors, so no response is lost. A managed schedule calls `/api/public/jobs/education-sheet-sync` every few minutes to run the same sync automatically.
- The student AI checklist accepts only non-sensitive answers (category, class/course, fee type, state, age group, ticked items, a short note rejected if it contains long numbers, emails or IFSC codes), is rate-limited per visitor IP, and stores nothing, so no contact, bank or Aadhaar details reach the model.
- Education Support no longer renders the student AI checklist; keep exam calculations and category syllabus browser-safe in exam.ts, and bilingual legal clauses in legal.ts with dedicated leaf pages, because policies do not implement an online exam or automatic award. Terms acceptance is required before the payment step, and policy navigation sits outside the form before the footer.
- Paid public AI tools that are not tied to a form (the prototype assessment) require a signed-in account plus per-account and per-address limits, so anonymous callers cannot spend AI credits.
- `requeue_all_google_copies` runs only with the service role after the server function confirms the caller is an admin, and uses static SQL per table.
- Every uploaded document/video in the listed private buckets (not site pictures or volunteer KYC) is listed by the service-only `queue_new_uploaded_files()` into `uploaded_files` during the same scheduled job, copied to the Drive folder (≤45 MB, else marked too large), and its Drive link reaches the "Uploaded files" tab through the usual queue trigger, so no upload screen needs its own Drive code.
- Every website form table, CRM leads and payments are copied to tabs of one Google Sheet (and applicant documents to one Drive folder) by AFTER INSERT/UPDATE triggers that queue rows in a server-only table, drained by a scheduled `/api/public/jobs/google-sheet-copy` run that upserts by the Record ID column with RAW values; the database stays the source of truth and hidden/private columns are never copied, so slow or failing Google calls never block a visitor.
- The Google Sheet and Drive folder that receive website copies are chosen in an admin-only settings row (link or auto-create from Admin → Google Sheet & Drive), read server-side with a short cache and the project secrets as fallback, so the destination can change without redeploying.
- Referral links use one browser-safe module (`referral.ts`) listing every form path; `?ref=` is remembered per tab by a shared hook and saved as each form's `coordinator_code`, so the existing CRM intake trigger routes the lead without per-form logic.
- Scheduled job routes accept GET (Vercel Cron) and POST with the same Bearer-secret check, and `CRON_SECRET` aliases `LOVABLE_CRON_SECRET` server-side, so the jobs run on either host.
- Volunteer programme rules live in browser-safe `volunteers/rules.ts` (tested) mirroring database/update-2026-11-15-volunteers.sql; dashboards read through the signed-in user's RLS via `volunteers/data.ts` and all money/KYC/ownership actions go through checked security-definer RPCs or the `volunteers_guard` invoker trigger, so employees see only their own volunteers; withdrawals are verified by Accounts and paid by a different Finance person (or admin) with UTR + proof.
- `/login` is the single default sign-in: the `my_dashboards()` security-definer RPC lists the caller's dashboards from existing access tables, `lib/dashboards.ts` (tested) opens one directly or offers a choice, and the shared shell shows only those dashboards as switch options, so access stays decided by the database. Sign-in pages offer no demo shortcut or credentials; any `@riloyd.demo` account is still ignored by `first_admin_setup_status`, so it can never claim first-admin setup.
- Every request (leave, WFH, expense, payment, tickets, volunteer requests) moves only through security-definer RPCs (`request_submit/act/comment/cancel`) following admin-editable `request_routes`; `requests.ts` mirrors the route, leave and maker-checker rules with tests, so the browser never decides approvals.
- Finance records (`fin_*`) are readable only by Accounts/Finance/Admin and written only by RPCs; a trigger locks reconciled entries and blocks deletes, and maker-checker (recorder ≠ verifier, step handlers distinct, approver ≠ payer) is enforced in the database, so corrections are always new adjustment entries.
- Integration credentials are AES-GCM encrypted with INTEGRATIONS_ENCRYPTION_KEY in `integration_connections` (no client grants), changed only by admin server functions in `integrations.functions.ts`; routes read them through `integrationCredentials()` with project secrets as fallback, and failures go through `integration_report` which alerts admins, so all integrations are managed from Admin only. Changing that key makes saved integration keys unreadable (re-enter them).
- Payment configuration, commission rates and payout rules are guarded by a trigger and change only through `critical_change_propose/decide` (a second admin, or the sole admin after 12 hours); settings tables log every change to `settings_change_log` with secret-like fields masked.
- Startups/Businesses/Manpower clients and the funding pipeline live in `venture_*`/`funding_*` tables; Admin alone moves stages (`funding_move`), a database trigger blocks any move past (or "funded" without) an uncleared mandatory jury round and jury stages cannot be removed, mirrored and tested in `ventures/rules.ts`; BDE/BDM see only assigned clients via `crm_can_access`, founders only their own company (`/client-portal`) and only public jury remarks, so the browser never decides progression.
